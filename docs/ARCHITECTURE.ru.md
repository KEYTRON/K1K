# Архитектура K1K

Язык: [English](ARCHITECTURE.md) | Русский

## Цели дизайна

1. **Маленькое привилегированное ядро.** В ring 0 живёт только то, что обязано:
   планировщик, адресные пространства, IPC, капабилити, вход в прерывания.
   Ошибка здесь фатальна (`kernel panic`), поэтому поверхность держим минимальной.
2. **Всё остальное — сервис.** Драйверы, файловые системы и подсистемы выше
   работают в ring 3 в собственном адресном пространстве. Падение убивает только
   эту задачу; супервизор пересоздаёт её. Без перезагрузки и без участия
   пользователя.
3. **Капабилити вместо «неявных прав».** Задача обращается к объектам ядра
   только через слоты своей таблицы капабилити. У каждого слота — маска прав,
   проверяемая на каждом сисколле. Нет UID, нет глобальных пространств имён,
   в которых можно «угадать» имя.
4. **Быстрые пути там, где это важно.** Передача сообщения заблокированному
   получателю — прямая (без копирования через очередь), путь сисколла —
   `syscall`/`sysret`, а для больших данных планируются shared-memory каналы,
   а не копирование сообщений.

## Загрузка

Limine (протокол, base revision 3) загружает ELF по адресу `0xffffffff80000000`,
настраивает 4-уровневую страничную адресацию с Higher Half Direct Map (HHDM)
всей доступной памяти, маскирует PIC/IOAPIC и передаёт управление в `kmain`
с выключенными прерываниями.

Порядок в `kmain`: serial → GDT/TSS → IDT → консоль на framebuffer → PMM → VMM →
heap → планировщик → IPC → MSR для syscall → ACPI/APIC → включение
прерываний → супервизор → сервисы.

## Прерывания

`arch/x86_64/acpi.rs` берёт RSDP у Limine (при base revision 3 это физический
адрес, поэтому таблицы маппятся в HHDM по мере надобности), обходит RSDT или
XSDT и разбирает MADT: адрес local APIC, включённые CPU, I/O APIC и
override'ы ISA-источников прерываний.

`arch/x86_64/apic.rs` включает local APIC BSP (spurious-вектор `0xFF`),
калибрует его таймер по каналу 2 PIT (one-shot 20 мс, gate через порт `0x61`)
и запускает в периодическом режиме на `TIMER_HZ` (1000). Все записи
перенаправления I/O APIC сначала маскируются; `route_isa_irq` затем
программирует запись для legacy IRQ, применяя полярность/триггер из override
MADT, если он есть. Legacy-PIC 8259 перемаплены подальше от векторов
исключений и полностью замаскированы.

Каждый вектор IDT указывает на сгенерированную asm-заглушку
(`trap_stubs.s`), которая пушит `(код ошибки, вектор)`, сохраняет все
регистры общего назначения, делает `swapgs`, если ловушка пришла из ring 3, и
вызывает `trap_dispatch(&mut TrapFrame)` (`trap.rs`). Диспетчер разбирает
исключения (убить пользовательскую задачу или паника), вектор таймера (32), а
все остальные векторы отдаёт в `irq::on_vector`, который пересылает их в
привязанный эндпоинт (если есть) и подтверждает. Раскладка векторов: 32 —
таймер, 34..49 — ISA IRQ 0..15, 64..127 — MSI-X, 255 — spurious. На выходе
заглушка меняет GS обратно для фреймов из ring 3 и делает `iretq`.

## Память

| Область | Адрес | Примечание |
|---------|-------|------------|
| Образ пользователя | от `0x0000_0000_0040_0000` | сегменты ELF `PT_LOAD`, права R / RX / RW по флагам сегмента |
| Стек пользователя | ниже `0x0000_7fff_ffff_0000` | 16 страниц, NX |
| HHDM | `0xffff_8000_0000_0000` (выдаёт Limine) | прямое отображение физической памяти |
| Куча ядра | `0xffff_9000_0000_0000` | 16 MiB, маппится при инициализации |
| Образ ядра | `0xffffffff80000000` | |

- **PMM** (`mm/pmm.rs`): один бит на фрейм 4 KiB, битмап лежит в самом большом
  usable-регионе. `alloc_frame`, `alloc_zeroed_frame`, `free_frame`.
- **VMM** (`mm/vmm.rs`): таблицы страниц загрузчика остаются таблицами ядра.
  Пользовательское `AddressSpace` — свежий PML4, записи 256..512 которого
  скопированы из PML4 ядра: верхняя половина общая, нижняя — приватная.
  Drop `AddressSpace` освобождает все таблицы и фреймы нижней половины.
- **Куча** (`mm/heap.rs`): `linked_list_allocator` поверх фиксированного окна.

## Задачи и планирование

У каждой задачи — потока ядра или сервиса в ring 3 — есть стек ядра на 64 KiB.
Переключение всегда идёт между стеками ядра (`arch/x86_64/context.rs`):
сохраняемые вызываемым регистры пушатся, `rsp` записывается в задачу,
загружается `rsp` следующей задачи, её регистры попаются, `ret`. Стек новой
задачи заранее заполнен так, чтобы `ret` привёл в `task_trampoline`, который
включает прерывания и вызывает точку входа.

Планировщик (`sched/mod.rs`) — round-robin с квантом 10 тиков (10 мс) при
1000 Гц.
На каждом тике таймера спящие с истёкшим дедлайном становятся готовыми; если
квант текущей задачи исчерпан и есть готовые, `schedule()` вызывается прямо
в обработчике IRQ (прерванный фрейм остаётся на стеке ядра этой задачи).

Состояния: `Ready`, `Running`, `Blocked` (ждёт на эндпоинте), `Sleeping`,
`Dead` (ждёт, когда супервизор её уберёт).

В ring 3 задача входит из своего потока ядра через `iretq`
(`context::enter_user`). При сисколле CPU переключается на стек ядра текущей
задачи (`PerCpu.kstack_top`, он же продублирован в `TSS.rsp0` этого CPU для
прерываний), поэтому вложенные ловушки и вытеснение внутри сисколла работают
без специальных случаев.

## SMP и per-CPU состояние

Bootstrap-процессор находит остальные через MP-ответ Limine и отпускает их по
одному (`smp.rs`). Перед стартом AP BSP выделяет ему `CpuTables` (GDT, TSS,
IST-стек) и блок `PerCpu`; AP загружает их, ставит общий IDT, программирует
свои MSR для syscall, регистрирует свой boot-контекст как idle-задачу,
запускает таймер своего local APIC и включает прерывания. Дальше это просто
ещё один CPU, берущий работу из очереди готовых.

`PerCpu` (`percpu.rs`) доступен через GS base: в режиме ядра `GS_BASE`
указывает на блок, а пока задача работает в ring 3, базы поменяны местами
(`swapgs` в заглушке syscall, в trap-заглушках и в `enter_user`), так что
пользовательский код не может ни увидеть, ни испортить указатель ядра.
`CR4.FSGSBASE` держится сброшенным. В блоке лежат текущая задача, idle-задача,
вершина стека ядра для входа в syscall, указатель на TSS и счётчик
переключений контекста.

Корректность между CPU держится на двух правилах в `sched/mod.rs`: задача, от
которой уходят, ставится обратно в очередь только в `finish_switch`, который
выполняется уже на новом контексте, когда старый стек больше не используется;
а `wake` помечает задачу `Ready`, но не ставит в очередь, пока у неё выставлен
`on_cpu`, — это сделает `finish_switch`. Супервизор так же забирает мёртвую
задачу только после того, как она покинула свой CPU. `Endpoint::recv`
регистрируется, помечает себя заблокированным и уходит в планировщик внутри
одной секции с выключенными прерываниями, поэтому отправитель на другом CPU
не может потерять пробуждение. Время идёт только по тику таймера BSP; тик
каждого CPU управляет его собственным вытеснением.

Дисциплина блокировок: каждый спинлок, который может взять обработчик
прерывания — планировщик, эндпоинты, таблица прерываний, консоль — и каждый
лок, который может взять код, уже держащий один из них, — куча ядра и PMM —
удерживается только с выключенными прерываниями. Иначе CPU A мог бы держать
кучу с включёнными прерываниями, получить тик таймера и закрутиться на локе
планировщика, который держит CPU B, сам ожидающий кучу. Обёртка аллокатора
кучи и точки входа PMM выключают прерывания именно поэтому, а обработчик тика
будит спящих без аллокаций.

## Объекты, капабилити, IPC

```
Task ── CapTable ── [slot] ── Capability { object, rights }
                                 object: Endpoint | Memory | Device | Irq | Port | Control
                                 rights: SEND | RECV | GRANT | MAP_READ | MAP_WRITE | DMA | SPAWN
```

`Endpoint` (`ipc/mod.rs`) — синхронный канал сообщений `[u64; 4]` плюс id
отправителя. `send` никогда не блокирует: если на эндпоинте кто-то заблокирован
в `recv`, сообщение пишется прямо в его inbox и он пробуждается; иначе оно
ставится в ограниченную очередь (`EAGAIN` при переполнении). `recv` блокирует
до прихода сообщения.

Сообщение может нести одну капабилити (`send_cap`). Отправитель должен иметь
на неё `GRANT`; получатель получает копию с правами `rights ∩ mask`, которая
вставляется в его таблицу при `recv`, а номер нового слота возвращается в
слове 3 (`NO_CAP` = `u64::MAX`, если ничего не приложено). Это единственный
способ передать полномочия между задачами — глобального пространства имён,
где объекты можно было бы «найти», нет.

`MemoryObject` (`obj/mod.rs`) — набор физических фреймов. `mem_create`
выделяет его (создатель получает `MAP_READ|MAP_WRITE|GRANT`), `mem_map`
маппит в адресное пространство вызывающего по адресу, выбранному ядром выше
`0x10_0000_0000` (только чтение, если у капабилити нет `MAP_WRITE`). Фреймы
возвращаются в PMM, когда исчезают последняя капабилити и последний маппинг;
при уничтожении адресного пространства разделяемые страницы размаппливаются
без освобождения. `mem_create_dma` выделяет физически непрерывные фреймы и
добавляет право `DMA`, которое открывает `mem_phys` — физический адрес,
нужный устройству.

`DeviceObject` оборачивает PCI-функцию, найденную сканированием при загрузке
(`pci.rs`, который также измеряет BAR'ы и включает memory decoding + bus
mastering при выдаче функции). `dev_info` описывает её; `dev_map` маппит
memory-BAR без кеширования в адресное пространство вызывающего. Страницы
устройств учитываются как разделяемые, чтобы при уничтожении адресного
пространства ядро не пыталось освободить MMIO-«фреймы».

`IrqObject` (`arch/x86_64/irq.rs`) представляет один вектор прерывания:
либо legacy ISA-линию, проведённую через I/O APIC (`irq::isa`), либо
MSI-X-запись 0 PCI-функции, нацеленную на свежий вектор (`irq::msix`, драйвер
получает её через `dev_irq`). `irq_bind` привязывает эндпоинт; каждое
прерывание становится сообщением `[vector, count]` в нём, отправленным из
trap-пути после EOI в APIC. Линии по уровню маскируются в I/O APIC, пока
драйвер не вызовет `irq_ack`. Капабилити `Port` дают диапазон портов
ввода-вывода x86 для `port_in`/`port_out` (контроллер клавиатуры 8042 живёт
на `0x60..0x64`).

`Control` — объект полномочий самого ядра; капабилити на него с правом
`SPAWN` позволяет задаче превратить ELF-образ, лежащий в объекте памяти, в
новый сервис под супервизором (`spawn`). Такая капабилити есть только у `fs`.

Половины канала — два разных объекта. `Endpoint::new_pair` возвращает связанную
пару: отправка в одну половину приходит в очередь другой, и каждая половина —
своя капабилити. Именно поэтому выражается «пусть сервис поговорит с
файловым»: `fs` держит принимающую половину, манифест может отдать
отправляющую сервису, и ни одно право не приходится расширять — пересечение
`RECV` с маской `SEND` дало бы пустое право и клиента, который не может
отправить.

## Драйверы и user space в ring 3

Ядро не содержит ни протоколов устройств, ни файловой системы:

- `kbd`: держит объект прерывания для ISA IRQ 1 и капабилити на порты 8042.
  Создаёт эндпоинт, привязывает к нему прерывание и на каждое сообщение
  вычитывает выходной буфер контроллера через `port_in` и декодирует scancode
  set 1. В ring 0 о клавиатурах не знает ничего.
- `blk`: драйвер NVMe. Получает контроллер как капабилити `Device`, маппит
  BAR0, запрашивает его MSI-X-прерывание (`dev_irq`) и привязывает к эндпоинту
  *до* включения контроллера, выделяет DMA-страницы под admin- и I/O-очереди
  (создаются с включёнными прерываниями на векторе 0), идентифицирует
  контроллер и namespace и обслуживает чтение блоков — засыпая на эндпоинте
  прерывания, пока команда в полёте, с запасным опросом, если объекта
  прерывания нет. Клиент прикладывает
  DMA-буфер (`REGISTER_BUF`, капабилити в сообщении, число страниц в старшей
  половине слова 0) и эндпоинт для ответов (`SET_REPLY`), затем шлёт `READ lba
  count`; `blk` отвечает `status, blocks, block_size`, сделав DMA в буфер.
  Константы протокола — в `k1k-rt::blkproto`.
- `fs`: FAT12/16/32 только на чтение (`user/svc/fs/src/fat.rs`) поверх этого
  протокола с общим DMA-буфером 64 KiB. Он же init: читает
  `/SVC/MANIFEST.TXT` и поднимает ровно то, что в нём перечислено.

Загрузка выглядит так: Limine → ядро → встроенные `kbd`/`blk`/`fs` (и демо
`ping`/`pong`) → `fs` монтирует диск → остальной user space приходит по
манифесту. Если драйвер упадёт, супервизор перезапустит его, и он заново
инициализирует своё железо.

### Манифест сервисов

`/SVC/MANIFEST.TXT` — список того, что запускается, по строке на сервис:

```text
# имя     образ          капабилити
hello     HELLO.EOF      fs
flaky     FLAKY.EOF
console   CONSOLE.ELF    fs,control
```

`#` начинает комментарий, плохая строка сообщается и пропускается, а не роняет
загрузку, и сервис стартует, только если он перечислен: файл, просто
положенный в `/SVC`, остаётся инертным. Имя образа — путь на томе, относительное
имя разрешается под `/SVC`.

Имена капабилити разрешает сам `fs` среди капабилити, которые держит он
(`fs` — отправляющая половина файлового канала, `control` — полномочие на
запуск), поэтому манифест может раздать только уже существующие в системе
полномочия, а опечатка становится ошибкой, а не тихим отсутствием доступа. Каждая
выданная капабилити становится слотом новой задачи по порядку манифеста;
супервизор передаёт это соответствие сервису в аргументе `caps=`, а
`k1k_rt::granted("fs")` его находит — сервису не нужно знать номер слота.

### Файловый протокол

Клиент с капабилити `fs` говорит с `fs` через разделяемый буфер, который сам
регистрирует; пути, листинги и содержимое файлов — байты в этом буфере, так что
сервису не нужно доверять указателю, а ядро не занимается файлами. По проводу —
по одному сообщению в каждую сторону:

```text
клиент → fs   w0 = операция, w1 = записано байт в блок запроса, w2 = сколько байт нужно под результат
fs → клиент   w0 = статус, w1 = arg0, w2 = arg1
```

Обе стороны даёт `k1k-rt`: клиент `file::FileClient` (`open`, `read`,
`read_all`, `stat`, `list`, `close`) и серверная `server::Server`, которая ведёт
клиентов по задачам и отвечает только на эндпоинте, который клиент
зарегистрировал. Две регистрации сервера — `CONNECT` (эндпоинт для ответов) и
`REGISTER_BUF` (разделяемый буфер) — независимы, так что клиент может слать их в
любом порядке.

То есть третьему сервису для файлов нужна только строка манифеста: `hello`
перечисляет `/SVC`, делает stat и читает `/README.TXT` и переживает любой свой
сбой (нет капабилити, нет файлового сервиса, нет такого пути).

IRQ клавиатуры — первый «драйвер как источник сообщений»: обработчик кладёт
сканкоды в эндпоинт ядра; сервис `kbd` держит единственную капабилити `RECV`
на него и потому является драйвером клавиатуры — декодирование сканкодов не
выполняется в ring 0, а при падении `kbd` супервизор его перезапускает.

## Сервисы и супервизор

`service/mod.rs` держит таблицу
`ServiceSpec { name, image, grants, dynamic, args }`. `spawn(idx)` создаёт
`AddressSpace`, загружает ELF-образ (`loader/mod.rs`:
статический ELF64, каждый `PT_LOAD` маппится с правами из `p_flags`, адреса
проверяются на принадлежность пользовательскому диапазону), маппит стек
64 KiB, кучу 4 МиБ (`USER_HEAP_BASE`) и одну страницу boot-info, вставляет
выданные капабилити и публикует задачу.

Id задачи резервируется заранее (`sched::reserve_task_id`), чтобы страница
boot-info могла нести уже окончательный id и быть заполнена до того, как любой
процессор сможет войти в задачу: сервис не должен увидеть недостроенное
адресное пространство. На странице лежат границы кучи и стека и аргументы
запуска; `k1k-rt` читает её, чтобы найти свою кучу и аргументы, а его
аллокатор инициализируется по ней при первом обращении — без вызова
инициализации из пользовательского кода.

Образ и аргументы хранятся до конца работы ядра, поэтому перезапуск создаёт
задачу ровно с теми же полномочиями, что и в первый раз. Сервисы собираются из
Cargo-workspace `user/` скриптом `kernel/build.rs` и встраиваются через
`include_bytes!`. `supervisor_main` работает потоком
ядра: убирает `Dead`-задачи (освобождая стек, адресное пространство,
капабилити) и для задач, принадлежавших сервису, пересоздаёт их. После трёх
перезапусков включается линейный backoff (200 мс × n, максимум 3 с).

`spawn_desc` (сисколл 22) — это `spawn` плюс список капабилити и блок
аргументов. Дескриптор лежит в адресном пространстве вызывающего:

```text
слово 0  ctl_slot   1  mem_slot    2  size       3  name_ptr
слово 4  name_len   5  n_grants    6  arg_ptr    7  arg_len
далее n_grants × { slot, rights }
```

Каждая выдача выводится из таблицы самого вызывающего — нужен `GRANT`, права
пересекаются, — так что полномочия только передаются дальше, но никогда не
расширяются. Слоты капабилити новой задачи нумеруются в указанном порядке, и
именно это сообщается в аргументе `caps=`.

### Куча сервисов

`k1k-rt` даёт глобальный аллокатор каждой программе ring 3: first fit по
списку свободных блоков, который ведётся по адресу и двусвязный, поэтому
`dealloc` сливает соседей за константу, а `realloc` растёт и ужимается на месте,
когда позволяет соседний блок. Две детали важнее, чем кажутся:

- Размер блока округляется до 16 байт, чтобы флаг «свободен» мог жить в бите 0
  слова размера: размер, не кратный двум, сделал бы флаг и размер
  неразличимыми.
- Полезная часть с выравниванием больше 16 не может начинаться сразу за
  заголовком, поэтому `payload - header` — не заголовок. Каждая полезная часть
  хранит расстояние до своего заголовка в слове под собой, и это позволяет
  `dealloc` снова найти блок.

`make test-heap` гоняет аллокатор на хосте с подменённой страницей boot-info и
проверяет список блоков — размеры, связи, разбиение, перекрытия и учёт — после
каждой операции 50 000 раундов амортизации. Он же часть CI.

Исключения в ring 3 (`#PF`, `#GP`, `#UD`, …) обработчики IDT направляют в
`sched::on_user_fault`, который помечает задачу мёртвой и уходит в планировщик.
То же исключение в ring 0 — паника ядра.

## ABI сисколлов (x86_64)

`rax` = номер, аргументы в `rdi`, `rsi`, `rdx`, `r10`; результат в `rax`.
`rcx` и `r11` портятся самой инструкцией; все остальные регистры ядро
сохраняет. Отрицательный результат — ошибка. Программы на Rust используют
обёртки из `user/rt` (`k1k-rt`).

| # | Имя | Аргументы | Результат |
|---|-----|-----------|-----------|
| 0 | `log` | `ptr, len` (≤ 4096) | 0 |
| 1 | `exit` | `code` | не возвращается |
| 2 | `yield` | — | 0 |
| 3 | `sleep` | `ms` | 0 |
| 4 | `send` | `slot, w0, w1, w2` | 0, `EPERM`, `EAGAIN` |
| 5 | `recv` | `slot, buf[4×u64]` (слово 3 = слот полученной капабилити или `NO_CAP`) | id задачи-отправителя, `EPERM`, `EFAULT` |
| 6 | `info` | `buf[2×u64]` → `uptime_ms, task_id` | 0 |
| 7 | `send_cap` | `ep_slot, cap_slot, rights_mask, w0` | 0, `EPERM`, `EAGAIN` |
| 8 | `cap_drop` | `slot` | 0, `EINVAL` |
| 9 | `mem_create` | `pages` (1..=1024) | новый слот, `EINVAL`, `ENOMEM` |
| 10 | `mem_map` | `slot, writable` | базовый адрес, `EPERM`, `ENOMEM` |
| 11 | `ep_create` | — | новый слот (`SEND|RECV|GRANT`), `ENOMEM` |
| 12 | `mem_create_dma` | `pages` (1..=64, непрерывно) | новый слот (`+DMA`), `EINVAL`, `ENOMEM` |

| 14 | `dev_info` | `slot, buf[14×u64]` | 0, `EPERM`, `EFAULT` |

| 16 | `spawn` | `ctl_slot, mem_slot, size, name_ptr \| len<<48` | id новой задачи, `EPERM`, `EINVAL`, `EFAULT` |
| 17 | `irq_bind` | `irq_slot, ep_slot` | 0, `EPERM` |

транслируются через таблицы страниц самой задачи, прежде чем ядро их тронет.

## Тестирование

`make test` собирает ISO, в `limine.conf` которого передаётся
`cmdline: autotest`. Ядро восемь секунд гоняет сервисы (`autotest=<секунды>`
меняет это), печатает сводку и выходит из QEMU через `isa-debug-exit` со
статусом 33 при успехе или 35 при провале. В логе должны быть: монтирование
тома, запуск обоих сервисов по манифесту, работа файлового сервера и чтение
`/README.TXT` сервисом `hello` — загрузка, которая запустила сервисы, но не
умеет отдать файл, считается провалом, а не успехом. Serial-лог остаётся в
`build/serial.log`.

`make test-heap` — тест аллокатора, описанный выше; CI гоняет оба, на BIOS и
через boot-тест K1OS на UEFI.
