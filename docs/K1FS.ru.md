# K1FS: нативная файловая система K1OS

Статус: проект v1, не реализация.

K1FS будет нативным writable-хранилищем K1OS и WARP. FAT остаётся
совместимым загрузочным и обменным форматом: /SVC можно положить на FAT,
но store пакетов, каталоги с длинными именами и атомарная активация не должны
быть ограничены FAT 8.3.

## Цели v1

- Файлы, каталоги и UTF-8 имена без ограничения 8.3.
- Extent-файлы вместо цепочек кластеров; дешёвое последовательное чтение
  архивов WARP.
- Атомарные create, rename, unlink и замена текущей версии пакета.
- Предсказуемое восстановление после отключения питания: либо старое
  состояние, либо новое, но не повреждённый каталог.
- Проверяемые CRC метаданных; ограниченное потребление RAM.
- Отдельный сервис ring 3 с capability только на блочное устройство. Ядро
  не получает парсер файловой системы или ключи.

Не-цели v1: POSIX-совместимость на уровне дискового формата, snapshots для
пользователя, дедупликация, компрессия и распределённая ФС.

## Дисковая модель и атомарность

Том имеет два superblock-слота A/B. Каждый хранит generation, корень
метаданных, параметры формата и CRC. Метаданные copy-on-write:

1. новые extent и страницы каталогов пишутся в свободные блоки;
2. их CRC проверяется до публикации;
3. записывается следующий superblock с generation + 1;
4. только после flush он становится корнем тома.

После сбоя монтировщик выбирает старший корректный superblock. Старые блоки
освобождаются только когда новый корень уже опубликован. Это даёт ровно
нужную WARP-семантику: новый пакет и его activation появляются вместе или
остаётся предыдущая рабочая версия.

## Шифрование K1FS-CRYPT (опционально)

Шифрование защищает владельца при краже устройства или получении offline
копии диска. Оно не является forensic-инструментом и не содержит
экспортёра данных, скрытого доступа, обхода пароля, скрытых томов,
принудительной разблокировки или режима для правоохранителей.

### Базовый режим

- Том генерирует случайный 256-битный DEK; им AEAD-шифруются данные,
  имена, directory entries и метаданные. Незашифрованными остаются только
  минимальный заголовок и key slots, нужные для монтирования.
- Passphrase не является ключом диска: Argon2id с уникальной 128-битной
  солью и сохранёнными параметрами выводит KEK, которым заворачивается DEK.
  Параметры выбираются владельцем под железо; рекомендуемые RFC 9106
  отправные точки — 64 MiB / t=3 для ограниченной памяти и 2 GiB / t=1,
  когда это допустимо.
- Ключи живут только в выделенной памяти сервиса, очищаются при lock/unmount
  и не пишутся в журнал, swap или логи.

### Постквантовый recovery slot

PQC нужно не для bulk-шифрования каждого блока: его задача — сохранить
безопасность обёртки ключа на годы. Для каждого добровольно добавленного
recovery recipient создаётся slot:

1. ML-KEM-768 инкапсулирует общий секрет под публичный ключ recipient;
2. из секрета и контекста тома выводится одноразовый KEK;
3. этим KEK AEAD-шифруется DEK;
4. в slot лежат только ML-KEM ciphertext, encrypted DEK, идентификатор
   алгоритма и salt/context.

Private key recipient никогда не хранится на томе. Recovery slot можно
добавить и удалить только после разблокировки обычным ключом владельца.
ML-KEM стандартизован как FIPS 203; K1FS обязан иметь versioned crypto
registry, чтобы смена алгоритма не ломала старые тома.

В v1 не обещаем магическую защиту от всех квантовых рисков: безопасность
данных также зависит от AEAD, KDF, энтропии, реализации и физической модели
угроз. Нужны независимый крипто-review и тестовые векторы до включения
K1FS-CRYPT по умолчанию.

## Модель угроз и границы

Защищаем: украденный выключенный носитель, offline imaging, перебор
passphrase с известным заголовком, повреждение при потере питания.

Не защищаем без дополнительных слоёв: уже разблокированную ОС, malware с
доступом к сервису K1FS, cold-boot/RAM capture, подменённый загрузчик.
Для последнего потребуются verified boot, измеренная загрузка и отдельный
аппаратный/внешний ключ.

## Порядок реализации

1. Довести FAT16 до controlled replace/rename как временный compatibility
   volume (root-level create и проверка стойкости записи после QEMU уже есть).
2. K1FS plain: A/B superblocks, allocator, extent, каталоги, CRC и crash
   tests с принудительным обрывом на каждой стадии коммита.
3. Встроить K1FS в отдельный ring-3 сервис и перевести WARP store/activation.
4. Добавить K1FS-CRYPT с passphrase slot и независимым review.
5. Добавить ML-KEM recovery slots только после аудита криптографического API.

## Формат v1: конкретные решения (зафиксировано при реализации, 2026-11-11)

Документ выше — проект; этот раздел фиксирует байт-формат, который mkfs и mount
уже реализуют (срез 1: `user/svc/fs/src/k1fs.rs`, хост-регрессия
`tools/k1fs-test.rs`, `make test-k1fs`).

- **Блок** — 4096 байт (8 секторов по 512 байт блочного протокола). Все
  структуры K1FS — целые блоки; номер блока × 8 = LBA.
- **Слоты A/B** — блок 0 и блок 1, по одному 4 KiB-суперблоку в каждом.
  Коммит пишет *другой* слот с `generation + 1`; только эта публикация меняет
  корень тома.
- **Заголовок суперблока** — первые 1024 байта блока, little-endian:
  magic `K1FS` (0..4), `header_crc32` (4..8, CRC32/IEEE байт 8..1024),
  `format_version` u32 = 1 (8..12), `header_size` u32 = 1024 (12..16),
  `generation` u64 (16..24, 0 = не писался, mkfs пишет 1),
  `root_block` u64 (24..32, `u64::MAX` — корня ещё нет),
  `total_blocks` u64 (32..40), `log_block_size` u32 = 12 (40..44),
  `flags` u32 = 0 (44..48), дальше резерв до 1024. Остальное в блоке — нули.
- **CRC** — CRC32/IEEE 802.3 (отражённый, полином 0xEDB88320): дёшево в ring 3,
  достаточно для метаданных.
- **Mount** — берётся слот с наибольшей `generation` среди прошедших
  magic/version/header_size/CRC и умещающихся на устройстве; при равенстве —
  слот A. Оба слота битые → `NoSuperblock`; слот структурно валиден, но геометрия
  не сходится с устройством → `Inval` (не путать с «K1FS тут нет»).
- **Контракт коммита** (реализовано срезом 5): новые метаданные в свободные
  блоки → проверка их CRC → запись другого слота с `generation + 1` → **flush** →
  публикация. Опкод `FLUSH` в blkproto и команда NVMe FLUSH (opcode 0x00) живут
  в ring-3 драйвере `svc/blk`; `k1fs::commit` флашит до и после записи слота,
  так что сбой с любой стороны оставляет предыдущий слот авторитетным. Хост-регрессия
  дополнительно гоняет обрыв питания на каждой записи коммита (FaultDisk).
- **Открытые вопросы**, не блокирующие срез 1 (решать следующими срезами):
  формат битмапа аллокатора и его место, формат inode/extent, страницы каталогов,
  сосуществование с FAT на одном диске (v1: K1FS форматирует свой образ целиком;
  интеграция с диском K1K — срез ring-3 сервиса), пределы имён (UTF-8, case,
  нормализация — по умолчанию case-sensitive), fsck.

## Метаданные v1: inode, extent, страницы каталогов (approved 2026-11-11)

Драфт (субагент) + ревью. Полная спецификация — байт-таблицы, коммит-последовательности
create/unlink/rename/replace, поведение mount-скана и лимиты — в коде среза 3
(`user/svc/fs/src/k1fs.rs`, module doc) и в этом разделе кратко:

- Каждый метаблок (inode/dirpage/ext) имеет 64-байтовый заголовок: magic `K1MB`,
  CRC32/IEEE байт 8..4096, block_type (1=INODE, 2=DIRPAGE, 3=EXT), flags,
  `owner_generation` (= sb.generation+1 на запись — ось времени для fsck),
  `self_block` (ловит перепутанную адресацию). Проверки: magic → тип → CRC →
  self → generation ≤ sb.generation.
- Inode = блок: mode (4=dir, 8=reg), size, для файла — inline-данные до 3984 B
  (INLINE) или extents (249 inline по 16 B: lba u64, nblocks u32, HOLE-флаг) +
  цепочка EXT-блоков (по 251 extent, ≤ 64 блоков); для каталога — `dir_first`/
  `dir_pages`, цепочка страниц `next_page`.
- Страница каталога: sorted entries переменной длины (name_len u16 ≤ 255,
  rec_len кратен 8, kind, target=блок inode), двоичный поиск внутри страницы.
  Удаление в v1 — compaction при CoW-переписывании; флаг DEAD зарезервирован,
  читатель обязан пропускать. `.`/`..` не хранятся — сервис синтезирует.
- Скан mount: BFS от root_block, visited-битмап (alias = повреждение и детектор
  циклов), данные из extents только помечаются (границы + не 0/1), не читаются.
  Битый CRC достижимого блока = честный отказ mount с номером блока.
- Коммит-последовательности: дети → родители → другой слот superblock → flush.
  WARP-активация = swap target записи в странице (1 страница + 1 inode + слот).
- Решения по открытым вопросам: hardlinks нет (identity = путь), цепочка страниц
  (не таблица), длина extent u32, CRC только метаданных, времен нет, sparse
  резервирован, имя ≤ 255 B UTF-8 case-sensitive без нормализации, reserve
  16 блоков, 1 inode = 1 блок, целые блоки, расширения — только через
  format_version.
